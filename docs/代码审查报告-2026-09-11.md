## 二、严重问题（16 条）

### 渲染与导出（R）

#### R1 ⚠️ 关闭「显示边框/背景」后预览 INFO 整体偏移
- **位置**：`src/components/preview/FooterInfo.vue:211-215`（关联 `:507-509`、`:328`）
- **问题**：预览 INFO 使用**原始** `state.padding / state.bgExpand`，而画板 CSS padding（`useCssVars.ts:94`）与导出（`exporter.ts:531` `applyShowToggles`）使用**生效值**。关闭边框/背景后 `padding=60` 仍被预览计入：INFO 元素整体偏移 60px、`scale = rect.width / canvasW` 分母偏大（拖拽位移 ≠ 鼠标位移）、底锚点 `frameContainerH - pad - bgExpand` 双重扣减。
- **修复**：FooterInfo 内改用 `applyShowToggles(state)` 后的 padding/bgExpand（或由 FrameContainer 注入生效几何）。

#### R2 ✅ 效果层预览与导出层级相反
- **位置**：`src/components/preview/EffectOverlay.vue:115`（`.effect-overlay { z-index: 4 }`）vs `src/core/exporter.ts:716-731`
- **问题**：预览中：背景(0) < 边框(1) < **效果(4)** < 照片(5) < INFO(6)，暗角/颗粒/水印被照片与信息层盖住，只在背景/留白区域可见；导出却在照片与 INFO **之后**绘制（覆盖全图）。组件注释声称"与导出一致"，但 z-index 与之矛盾。
- **修复**：二选一并统一——把预览 `.effect-overlay` 提到 INFO 之上（z-index > 6），或把导出改为在照片之前绘制效果层（需确认产品意图）。

#### R3 ⚠️ 颗粒缓存可达 GB 级
- **位置**：`src/core/bgRenderer.ts:280-315`（关联 `exporter.ts:719`）
- **问题**：`grainCache` 以 `w×h:strength:seed` 为键、上限 4 条；导出画布尺寸可达 12800×8800（≈450MB/张），4 条即 GB 级常驻内存。且每张新建需 `createImageData` 整幅 + `floor(w*h/4)*strength ≈ 2.8e7` 次主线程随机循环。
- **修复**：导出路径不走该缓存（生成一次），或把噪点做成固定 128px 瓦片按设计比例平铺（Pattern）。

#### R4 ✅ 批量导出单张失败中断整批
- **位置**：`src/components/layout/ExportPanel.vue:329-353`
- **问题**：`try` 包住整个 `for`，任何一张失败（损坏 JPEG、超画布上限、写盘失败）都中断整批；`failed` 只记录 1 条而 `total` 仍显示全部，用户以为有图可重试。
- **修复**：`renderOne` / `writeBlobTo` 包进 per-item `try/catch`，失败 push 后 `continue`。

#### R5 ⚠️ 导出边界校验 NaN 漏洞
- **位置**：`src/core/exporter.ts:466-469`（`Math.max(1, NaN)` 仍为 NaN）、`:497`、`:561-563`
- **问题**：`photoCrop` / `photoRotation` 为 NaN/undefined（旧数据/导入数据）时 `canvasW > MAX_DIM` 恒 false，最终只抛「canvas.toBlob 失败」；且只比较单边 16384，未管总像素/面积上限（iOS Safari ≈16.7M px）。
- **修复**：入口对源尺寸/旋转/crop 做 `Number.isFinite` 校验；对 `canvasW * canvasH` 加面积上限，超限给出明确文案。

### 状态与持久化（S）

#### S1 ✅ 批量导入/启动还原污染当前照片参数并写进历史
- **位置**：`src/composables/useLibrary.ts:316-324`（addFiles）、`:525-537`（addLocalEntries）；`src/platform/desktop.ts:76`；`src/App.vue:170-182`
- **问题**：`applyExifParsed()` 对共享 `frameConfig` 发 `patch()`（exifText/exifRaw/dateText/cameraModel/brand/lensText + show* 开关）。导入 N 张 = 对全局 state 连续 N 次覆盖，**最后一张的 EXIF 残留**成为当前活动照片的显示值。启动路径更糟：`void restoreLibrary()`（不 await，`desktop.ts:76`）与 `restoreActive()`（`main.ts:38` → `App.vue:182 loadCursorFor`）并发——最终 state 是「当前照片 + 最后导入照片 EXIF」的混合体；用户随后动一下滑块，`recordEdit` 就把混合快照写进**当前照片**历史链（永久）。附带：无 EXIF 的照片会继承上一张的品牌 Logo（`brandId` 缺省时不清）。
- **修复**：EXIF 补丁改为构造 `exifPatch` 对象——仅当 `item.id === activeId` 时应用；其余并入该照片自己的 `importPhoto(id, {...base, ...exifPatch})` 快照。批量导入结束后统一 `loadCursorFor(activeId)` 重放。`restoreLibrary()` 与 `restoreActive()` 串行化。

#### S2 ⚠️ 删除照片后历史链"复活"（DB 孤儿永不清除）
- **位置**：`src/composables/useHistory.ts:599-607`、`:220-237`（debounceTimer/pendingKey）；`src/composables/useLibrary.ts:94`、`:579-588`
- **问题**：`removePhotoHistory()` 只判断 `pendingCommit?.photoId`，**未判断 `pendingKey`**。时序：拖动滑块（防抖计时器启动）→ 点删除（`pendingCommit` 仍为 null）→ 删链成功 → 400ms 后 `flushPending()` → `ensureChain` 从 DB 重载 → `recordEdit` → `putHistoryNode` **把节点写回 IDB**。结果：永不回收的孤儿链（`clearAllGlobal` / `countAll` / `deletePhotoChains` 全仓库无调用点，无回收入口）；`clearAll()` 清空图库同理。
- **修复**：`removePhotoHistory()` 内改为 `if (pendingCommit?.photoId === photoId || pendingKey?.photoId === photoId) await flushPending()`，并在此之前无条件 `clearTimeout` / `cancelAnimationFrame` / `pendingKey = null`；`useLibrary.remove()/clearAll()` 先 `await flushPending()` 再删。

#### S3 ✅ objectURL 多路径泄漏
- **位置**：`src/composables/useLibrary.ts:310-312`、`:508-523`（尤其 `:511`）、`:158-168`（`:166`）
- **问题**：
  1. `makeThumbUrl(...).then(...)` 异步回填：若缩略图生成期间（限流排队 + 解码数百 ms）条目被删除，`remove()` 时 `thumbUrl` 仍为 undefined → `releaseUrl` 空转 → promise resolve 后把 blob URL 写到游离对象上，**永不 revoke**；
  2. 桌面端 `thumbFor` 磁盘缓存分支 `URL.createObjectURL` 同样可能落在已删条目上；
  3. `readSize()` 的 `img.onerror` 分支直接 resolve，**不 revoke** URL，每个解码失败文件泄漏一个全尺寸 objectURL。
- **修复**：回填前判存活（`if (!items.includes(item)) { releaseUrl(t); return }`）；`readSize` 统一在 `onload/onerror` 两分支先 revoke 再 resolve。

#### S4 ⚠️ IndexedDB 静默失败 + rejected promise 永久缓存
- **位置**：`src/composables/useHistoryDB.ts:24-47`（`dbPromise`）；`src/composables/useHistory.ts:292`、`:294`、`:315`、`:440`、`:463-464`
- **问题**：所有写入 `void putHistoryNode(node).catch(() => {})` 全静默——配额超限（每节点是整份 FrameConfig）、事务中止、IDB 被禁用均无声。内存链与 DB 分叉：UI 显示 20 步、重启只剩 3 步。`openDB()` 把 rejected promise 永久存进 `dbPromise`（无 reset/retry/onblocked/onversionchange），一旦首开失败，**本次会话全部 undo/redo/切图恢复静默失效**。
- **修复**：`onerror` 时 `dbPromise = null` 允许重试；补 `onblocked` / `onversionchange`；写入失败 `reportRuntimeError` + 首次失败 Toast；`QuotaExceededError` 给可操作提示。

### Rust 平台层（T）

#### T1 ⚠️ asset 协议 scope `"**"`：任意路径可读
- **位置**：`src-tauri/tauri.conf.json:17-22`（scope）、`:13`（`withGlobalTauri: true`）、`:16`（CSP connect-src 含 `asset:`）
- **问题**：`lib.rs:7` 声明的安全模型是"WebView 禁止直接 fs，全部经 Command IPC"，但 `asset: "**"` 给了渲染进程一条**绕过全部命令逻辑**的任意文件读取通道（`fetch('http://asset.localhost/C:/Users/x/.ssh/id_rsa')`）。配合 `withGlobalTauri: true`（`window.__TAURI__.core.invoke` 对任何同源脚本可见），一旦 XSS / 依赖投毒 / 解码器漏洞，第一步即可拿到全盘读能力（并与 `write_file_base64`、`open_external` 组成完整杀伤链）。
- **修复**：① asset 改为**动态白名单**（自定义协议 `register_uri_scheme_protocol`，或运行时把「已导入 catalog 的目录」加入 scope），至少排除系统目录;② 关闭 `withGlobalTauri`，改用打包的 `@tauri-apps/api/core`（`env.ts:4-6` 已兼容 `__TAURI_INTERNALS__`）；③ IPC 侧对 path 做校验（见 T3）。

#### T2 ⚠️ `open_external` 未校验 scheme：可执行任意程序
- **位置**：`src-tauri/src/lib.rs:1145-1156`（`open_external`）、`:763-800`（`shell_open`）
- **问题**：`shell_open` 用 verb `"open"` 调 `ShellExecuteW`，对 target 零校验。`\\attacker\share\x.exe`、`file:///C:/x.exe`、`.bat`、`ms-msdt:` 等都会被 shell 关联执行/拉起——一次 `invoke('open_external', {url})` 即代码执行原语（当前唯一调用点在 `PreferencesModal.vue:311-318`，但 IPC 面本身已暴露）。
- **修复**：Rust 侧白名单——仅允许 `https://` 前缀（可再收紧到 github.com/yuhaowang774）；显式拒绝含 `\\`、`file:`、首段冒号等输入。

#### T3 ⚠️ AppData 目录 JSON 非原子写 + 前端并发 fire-and-forget → 撕裂/图库丢失
- **位置**：`src-tauri/src/lib.rs:513-517`（`write_app_json`，`fs::write` 直接截断写）、`:374-391`；`src/platform/catalog.ts:91-110`（`persist`）、`:169-181`（每张照片 persist 一次）、`:215-220`
- **问题**：
  1. **并发撕裂**：导入/还原 2000 张 = 数千次互不等待的 `write_app_json`，Tauri 并发执行 → `truncate + write_all` 落同一路径必然交错 → 半截 JSON；`parse()` 的 catch 会把损坏文件当空目录，此后任意 persist 把"空目录"写回 → **图库永久丢失**；
  2. **原子性**：即使串行，进程被杀/断电同样产生截断文件；
  3. O(N²) 写放大：大图库导入时磁盘写入可达 GB 级（`catalogSetActive` 每次切图写全量含全部 meta 的大 JSON）。
- **修复**：Rust 侧临时文件 + `sync_all` + 原子 `rename`，内容加长度上限；前端 `persist()` 300–500ms 去抖 + 脏标记合并 + 单飞串行（`inflight` Promise），失败 `reportRuntimeError` 提示。

#### T4 ⚠️ 绿色版自更新下载：无大小上限 + 用服务器 Content-Length 预分配
- **位置**：`src-tauri/src/lib.rs:1054`（`let total = resp.content_length().unwrap_or(0)`）、`:1057`（`Vec::with_capacity(total as usize)`）、`:1059-1067`；`Cargo.toml:35`（`panic = "abort"`）
- **问题**：`total` 完全由服务端/MITM 控制，`with_capacity` 可被诱导为数十 GB 预留 → 分配失败即 **abort**（release 下进程直接死）。`buf` 无上限、验签前不落盘。签名校验不可绕过，但**可用性**被服务端单方面掌控。
- **修复**：`cap = total.min(MAX_EXE_BYTES)`（如 200MB）+ 分块熔断；改为"边下边写 `.part`（不可执行）→ 全量验签通过后 rename 为 `.new`"。

### UI 交互（U）

#### U1 ✅ 快速 A→B→A 切换照片：过期加载覆盖当前照片
- **位置**：`src/App.vue:154-157`（同照片守卫），配合 `:165-166`、`:171-193`
- **问题**：A 显示中 → 点 B（`switchSeq=1`、`loadingUrl=B`、`await loadImage(B)` 数秒）→ 再点回 A：`photoSrc` 仍是 A.url → 命中守卫**直接 return**，`switchSeq` 不变、B 加载不被作废。B 完成后 `seq(1) === switchSeq(1)` → 执行 `loadCursorFor(B)` / `photoSrc=B` / `bgImage=B`。结果：图库选中 A，画布与参数是 B。

#### U2 ✅ 全局快捷键与弹窗/编辑器冲突
- **位置**：`src/App.vue:206-234`（`:225-227` Esc、`:228-233` Delete）；`GlassModal.vue:59-74`、`PreferencesModal.vue:338`、`UpdateModal.vue:47`、`ExportPanel.vue:548`、`PhotoEditor.vue:307`
- **问题**：① 所有弹窗（GlassModal / 首选项 / 更新记录 / 导出预览 / 照片编辑器 / 使用指南）均无 Esc 关闭处理（首选项按钮 title 却写着「关闭 (Esc)」），Esc 被全局 `resetView()` 吃掉——用户按 Esc 得到"看不见的视图复位"；② 弹窗打开时 ←/→/Delete 仍生效：在照片编辑器里按 → 会把本地 `rotation/crop`（旧照片算出的）`patch` 到**新照片**上；焦点在任意按钮时 Backspace/Delete 触发移除确认弹窗。
- **修复**：加统一的浮层栈判定（有顶层遮罩时 onKey 直接跳过 ←/→/Delete）；GlassModal 等统一加 Esc→close（`stopPropagation`），Esc 被弹窗消费时不再复位画布。

#### U3 ⚠️ 面板拖拽监听泄漏（幽灵拖拽 + 组件实例泄漏）
- **位置**：`src/components/layout/Filmstrip.vue:134-148`（清理仅清 timer，未 removeEventListener）、`LeftPanels.vue:28-41`、`ControlPanel.vue:136-150`（均无 `onBeforeUnmount`）
- **问题**：三处同一份拷贝——`onDown` 里 `window.addEventListener('pointermove'/'pointerup')`，只在 `onPointerUp` 里移除。pointerup 丢失（pointercancel、`window.alert/prompt` 抢焦点、Alt-Tab）则监听器永久驻留：此后鼠标移动就持续改面板宽度（幽灵拖拽）并叠加新监听；若组件已卸载，闭包持有整个组件子树无法回收。`Workspace.vue:223-228`、`Filmstrip.vue:76-81` 的右键菜单 `once` 监听同理。

## 五、复核确认项（非问题，供对照）

来自 Rust 平台层深度复核，确认以下设计是**安全/正确**的，避免后续误改：

- **minisign 验签不可绕过**：公钥来自编译期嵌入的 `tauri.conf.json`（`lib.rs:953-962`，渲染进程无法改写）；`allow_legacy=false`（`lib.rs:982`）只接受 prehashed 签名；`pk.verify` 在 `fs::write` **之前**执行（`lib.rs:1068-1070`），"先验后写"顺序正确。
- **绿色版批处理无命令注入**：脚本纯 ASCII、路径全部由 `%~dp0` 运行时展开（`lib.rs:1103-1104`），中文/空格/`&`/`%` 无法进入解析（缺陷仅是 T11 的改名问题）。
- **`set_gpu_preference_mode` / `reveal_path` 无 shell 解析**：前者经 `Command::args` 传参（`lib.rs:734-741`），后者直接 spawn `explorer.exe`（`lib.rs:835-839`）。
- **`read_file_head` 上限有效**：`len` 被 `min(8MB)` 限幅（`lib.rs:276`），读循环正确处理 `r==0`；`read_image_meta` 对 JPEG 的 `seek(0)` 回卷正确。
- **更新检查链路现状（本次审查）**：安装版/绿色版的**下载-验签-安装-重启**链路完整；但"检查更新"目前**仅手动**（`PreferencesModal.vue:174`），启动时无自动检查与主动提醒（属功能缺口，见第六节）。
- **依赖安全**：`npm audit` 仅 dev 依赖告警（vitest/esbuild 的 dev server 类漏洞），不影响发布产物；修复需升 vitest 5（大版本），可暂缓。
